## 一、一句话说清这个项目

**币安钱包里要新开一个「理财」货架，卖的是"链上包装过的现实世界理财产品"。我负责的是：让 App 上显示的每一个数字（收益率、净值、我赚了多少）都是对的。**

就这么简单。剩下所有复杂度都是从这一句话里长出来的。

## 二、先搞懂 RWA 是什么

**RWA = Real World Assets = 真实世界资产**。

以前链上理财的收益从哪来？基本都是"币圈自己玩"——比如借币给别人收利息、给交易所提供流动性拿手续费。这些收益跟现实世界没关系，币圈冷了收益就没了。

RWA 就是把**现实世界里本来就在赚钱的东西搬上链**：

| 现实世界的东西 | 上链之后变成 | 本项目里的例子 |
|--------------|------------|--------------|
| 美国国债 | 一个能在链上转账的代币 | Ondo 的 USDY |
| 巴西商户的信用卡应收账款 | 一个代币 | Nest 的 nOPAL |
| 再保险合同（保险公司的保险） | 一个代币 | Re、OnRe |
| 实物黄金 | 一个代币 | Unitas XGLD、XAUE |
| 给 AI 公司买显卡的贷款 | 一个代币 | USD.AI 的 sUSDai |
| 美股 ETF、期权策略 | 一个代币 | Ondo QYLDon、DMZ rAI |

**为什么用户会买**：收益率比链上原生产品稳（因为底层是真实资产在赚钱），4%～15% 都有。
**为什么公司要做**：现在钱包的 DeFi 板块缺这类产品，RWA 赛道整体规模已经 340 亿美元，机构都在进场。

## 三、这里面有四层，搞清楚层次就不会乱

这是理解一切的关键。举 **Nest 的 nOPAL** 为例：

```
第 1 层｜真实资产    巴西商户的信用卡应收账款
                    （商户今天卖了货，钱要 30 天后才从银行到账，
                      现在有人愿意打折提前买走这笔钱）
                              ↓
第 2 层｜协议        BlackOpal 这家公司专门做这个生意，
                    Nest 把这个生意包成一个"链上金库（vault）"
                              ↓
第 3 层｜凭证代币    用户存 100 USDT 进去，
                    拿到一个叫 nOPAL 的代币 —— 相当于"存款凭证"
                              ↓
第 4 层｜我们        钱包要显示：你有多少 nOPAL、值多少钱、
                    赚了多少、年化多少 → 这就是"数据解析"
```

**我的工作在第 4 层。** 但要把第 4 层做对，必须理解 1～3 层——因为**不同协议的第 2、3 层设计差异极大，会让第 4 层的算法完全不同**。这就是为什么要做这 16 篇调研。

## 四、「凭证代币」是什么？拿银行类比

你去银行存定期，银行给你一张**存单**。存单本身不是钱，但它证明"我有多少钱在里面 + 到期能拿回多少"。

**凭证代币就是链上的存单**（英文叫 receipt token / share token / LP token，看到这几个词都是一个意思）。

| | 银行存单 | 链上凭证代币 |
|---|---------|------------|
| 你手里拿着 | 一张纸 | 一个代币（如 nOPAL、XGLD、sUSDai） |
| 证明什么 | 我存了多少 | 我占这个金库的多少份额 |
| 怎么拿回钱 | 到银行取 | 把代币还给合约，换回本金+收益 |

**所以"解析用户持仓"的本质就是**：看用户钱包里有多少个凭证代币 → 换算成"值多少美元"。

## 五、最重要的一个概念：NAV（净值）

这个词你会在所有文档里看到几百次，务必搞懂。

### NAV 是什么

**NAV = Net Asset Value = 净值 = 一个份额现在值多少钱。**

跟买基金一模一样。你买基金时看的"单位净值 1.0523 元"，就是 NAV。

### 为什么它这么重要

因为**大多数链上理财产品，收益不是给你发钱，而是让你手里那份东西变贵**。

举例（这个例子请记住）：

```
第 1 天：你存 100 USDT，NAV = 1.00，你拿到 100 个凭证代币
第 30 天：策略赚钱了，NAV 涨到 1.01
         你手里还是 100 个代币（数量没变！）
         但现在值 100 × 1.01 = 101 USDT
         → 你赚了 1 USDT
```

**关键点：代币数量一直不变，是"每个代币值多少钱"在涨。** 所以：

- 想知道用户持仓值多少钱 → `代币数量 × NAV`
- 想知道用户赚了多少 → `数量 × (现在的 NAV − 买入时的 NAV)`
- 想画一条收益曲线给用户看 → **需要每天记一次 NAV**

### 「NAV 天级打点」是在说什么

"打点"就是**每天定时抄一次表，存到数据库**。

为什么必须每天存？因为**链上合约只告诉你"现在"的 NAV，不告诉你"上个月"的**。就像温度计只显示当前温度，你想画一个月的气温曲线，就得从今天开始每天记一次。

这就引出项目里一个真实的难题——

### 「NAV 历史回溯」为什么是个难题

用户打开详情页，想看"过去 1 年的净值走势"。但我们才刚开始记，只有 3 天的数据，怎么办？

理论上可以"回溯"：区块链的历史数据都在，可以让程序倒着一天一天去查过去每一天的 NAV。但这需要特殊的节点（叫 archive node，存了全部历史状态），跑起来慢、贵，而且**有些协议的 NAV 不在链上算，是链下推过来的**——那就真的查不到历史了，只能找项目方要。

> 📌 所以 PRD 待确认事项第 1 条写的「NAV 历史数据回溯方案确认（能跑多久的历史数据）」就是这个意思，它挂在**我名下**。

## 六、三种记收益的方式（这是全项目最实用的知识点）

我调研 20 个产品后发现，链上产品记收益只有三种玩法。**认出是哪一种，算法就定了。**

### A 类：净值涨（最常见，本轮 7 个里有 5 个确定是这类）

```
你的代币数量：100 → 100 → 100（永远不变）
NAV：        1.00 → 1.01 → 1.02（往上涨）
```
**类比**：买基金。份额不变，净值涨。
**本轮例子**：Nest nOPAL、Unitas XGLD、OpenTrade PRIME+、Ember、Re
**算法**：`收益 = 数量 × (现NAV − 买入NAV)` ✅ 最简单

### B 类：份额涨（少数）

```
你的代币数量：100 → 101 → 102（自动变多）
NAV：        1.00 → 1.00 → 1.00（永远是 1）
```
**类比**：余额宝。你不用管净值，就看余额自己涨。
**专业叫法**：rebasing（重定基）
**本轮例子**：**Ondo USDY —— 待定！** Ondo 同时发了两个版本：USDY（净值涨，A 类）和 rUSDY（余额涨，B 类）。我们接的是哪个还没确认，这是本轮优先级最高的技术判断之一
**算法**：直接看余额变化。
🔴 **坑**：这类产品的 **NAV 永远是 1，画 NAV 曲线是一条毫无意义的直线**。所以详情页**不能给它配 NAV 图表**。

### C 类：直接发现金（本项目只有 1 个）

```
你的代币数量：100 → 100 → 100（不变）
NAV：        1.00 → 1.00 → 1.00（也不变！）
但每周有 USDT 打进你的钱包 ← 收益在这
```
**类比**：买股票收股息。股价没涨，但每季度给你打钱。
**本项目例子**：**DMZ 的 rAI**（每周发 USDT）
🔴 **这是全项目最大的坑**：如果按 A 类的公式算（`数量 × NAV 变化`），算出来是 **0 收益**——因为数量没变、NAV 也没变！但用户实际每周都在收钱。

**正确公式**：
```
DMZ 的收益 = 数量 × NAV 变化  +  历史上收到的所有 USDT 派息之和
                              ↑ 这一项绝对不能漏
```

而且更麻烦的是：派给用户的 USDT 已经进了用户钱包，**用户可能已经花掉了**。所以不能看"现在钱包里有多少 USDT"，必须去查**历史上每一笔派息转账记录**。

> 📌 这就是我在 README 里列的三大结论之一，需要专门找后端（Jackson / Calvin）对齐一次。

## 七、另外几个必懂的词

### APY（年化收益率）

**APY = 一年下来能赚百分之几。** App 上大大的"12.5%"就是它。

新手最容易犯的错：**直接把项目方官网写的数字抄过来**。为什么不行？

我调研时发现，USD.AI 这一个产品，不同来源写的收益率有 **4 个版本**：8%、10-15%、13-17%、20%。为什么？因为它们说的是不同的东西：

| 数字 | 其实是什么 |
|------|-----------|
| "目标 15%" | 项目方的**期望**，不是实际 |
| "过去一年平均 13%" | **历史**表现 |
| "当前 7 日年化 8%" | **最近 7 天**的实际表现 ← 这个才靠谱 |
| "最高 20%" | 通常**含代币奖励/积分**，不是真金白银 |

**正确做法**：我们自己算。有了每天的 NAV，就能算：
```
7 日年化 = (今天的NAV ÷ 7天前的NAV) 开 52 次方 − 1
```
（不用记公式，记住"用我们自己记的 NAV 算，别抄官网"就行）

### PNL（盈亏）

**PNL = Profit and Loss = 赚了还是亏了。** App 上的"Total Earnings +$130.68"就是它。

三件事要知道：

1. **PNL 可能是负数**，PRD 明确允许显示负值（红色带减号）。因为 NAV 会跌。
2. **我们中台只提供"每天的快照"，实际的加总计算是业务后端（Jackson）做的。** 分工是：我给原始数据，他做聚合。
3. **口径必须提前对齐**，否则同一笔钱两边算出来数字不一样，上线后对不上账。

### 「解析」到底是什么意思

你会天天听到"这个协议解析了吗"。

**解析 = 让我们的系统能读懂某个协议的链上数据。**

区块链上的数据是一堆二进制，不同协议的合约结构完全不同。我们得针对每个协议写一段代码，告诉系统"这个位置是用户余额、那个函数能查 NAV"。这段适配工作就叫解析。

**所以「接一个新协议」的成本，主要就是写这段解析代码。** 协议机制越标准，成本越低；越特殊（比如 DMZ 的派息型、Solana 链的），成本越高。

## 八、「六个数据维度」是在说什么

项目表格里那六列打勾的，就是每个协议要做的六件事：

| 维度 | 通俗解释 | 对应 App 上哪里 |
|------|---------|---------------|
| **实时解析** | 用户现在有多少持仓、值多少钱 | "My Position $7,100" |
| **交易历史解析** | 用户什么时候存的、什么时候取的 | History 那一栏 |
| **池子自发现** | 项目方新开一个池子，系统能自动发现，不用我们手动加 | 后台运营效率 |
| **APY** | 年化收益率 | 卡片上那个大大的百分比 |
| **NAV 历史** | 每天的净值，用来画曲线 | 详情页的折线图 |
| **PNL** | 赚了多少 | Total Earnings / Yesterday Earnings |

**当前进度**：7 个已确认的协议里，只有 Nest 和 Unitas 完成了前 4 项，**NAV 历史和 PNL 全表 0 完成**。

📌 **这两项正好就是 RWA 相比普通理财产品新增的需求，也就是本项目 8 月底要交付的核心工作。**

## 九、为什么我一直在纠结「赎回」这件事

这是我调研后发现最严重的问题，值得单独讲。

### 用户预期 vs 现实

App 上标「Flexible（活期）」，用户的理解是：**随时能取，像余额宝一样。**

但我核对官方文档后发现，原先 20 个产品里有 6 个标着"活期"实际根本不是。**收敛到 7 个之后，这个问题只剩 1 个**（其余 5 个都在暂不调研组里）：

| 协议 | 表格标的 | 官方文档实际写的 | 是否在本轮范围 |
|------|---------|---------------|:---:|
| **Re 的 reUSDe** | 活期 | **一个季度才处理一次赎回**（同协议的 reUSD 是即时赎回，没问题） | ✅ **在** |
| USD.AI | 活期 | 30 天一个周期 + 排队，人多要排好几个月 | 出范围 |
| OnRe | 活期 | 季度赎回，每季度只有开头 30 天能申请 | 出范围 |
| Theo | 活期 | 排队，平均两周 | 出范围 |
| Asseto NGI+ | 活期 | 私募基建股权基金，通常有锁定期 | 出范围 |
| DigiFT pEAK | 活期 | 对冲基金，赎回条款很严 | 出范围 |

📌 **这就是"收敛范围"的价值**：一次范围决策，把 6 个坑消掉了 5 个。剩下的 Re 也有解 —— **先只上 reUSD（即时赎回），reUSDe 等赎回窗口方案做完再上**。

### 为什么这是大事

**如果不改，会出现这种情况**：用户看到"活期"，存了 1 万块，一周后想取，发现要排队 3 个月。这是**产品事故级的用户预期错配**，客诉会炸。

### 顺带影响我的技术方案

PRD 要求赎回时返回一个 **request ID**（申请单号）+ 状态。为什么需要单号？因为赎回不是一步完成的：

```
即时赎回的协议：  点赎回 → 到账     （不需要单号，一步到位）
排队赎回的协议：  点赎回 → 拿到排队号 → 等 → （可能只到账一部分）→ 全部到账
                          ↑ 需要单号来追踪这个过程
```

我之前给的结论是"只返回交易成功/失败可行，要关联最终赎回结果得重构系统"。但调研后发现：**对 USD.AI 这种可能排队几个月、还可能只到账一部分的产品，只返回"交易成功"用户会误以为钱到了。**

📌 所以我的建议是：**一期优先上即时/T+N 赎回的协议**，排队型的等赎回状态方案做完再上。

## 十、我这个岗位到底每天在干什么

说白了就三件事：

### 1. 对齐口径（占比最大）

"口径"= 大家对同一个数字的定义要一致。

举个真实例子：PRD 里已结束产品要显示"Invested（投资金额）"。这个数字取什么？
- 结束时的余额？→ 可能已经全赎回了，显示 0，用户懵
- 平均值？→ 含义不清
- **周期内的最高余额** ← 最后定的方案，还要加个 tooltip 解释

这就是"对齐口径"。20 个产品 × 6 个维度，全是这种活。

### 2. 追要东西

主要是找项目方要：
- **合约地址**（没这个啥都干不了，我这轮 16 篇里绝大多数还是空的）
- 赎回条款细节
- 历史 NAV 数据
- 特殊协议的 API

### 3. 追待确认项

每篇协议文档的第 9 章「待确认清单」，都写清了"问什么问题、问谁"。这就是我的待办清单来源。

## 十三、接下来按这个顺序做（已按收敛到 7 个更新）

1. **先追合约地址** —— 这是最长的前置依赖，没有地址一切都开不了工
   → 最快的路径是**拿几条真实交易 hash**（比等项目方回复快，而且不会拿到过期信息）。清单见 [../03-参考/需要提供的交易Hash清单.md](../03-参考/需要提供的交易Hash清单.md)

2. **定 Ondo 是 USDY 还是 rUSDY**（第六节的 A 类 vs B 类）
   → 这**一个判断**决定：要不要天级打点 NAV、详情页要不要配 NAV 曲线、PNL 用净值差还是余额差。**定错了整套返工**，所以优先级很高

3. **找 Jackson / Calvin 单独对齐 DMZ 的 PNL 公式**
