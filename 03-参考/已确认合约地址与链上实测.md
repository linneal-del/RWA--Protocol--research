### 🔴 三个必须让中台知道的结论

**1. Re 不是 ERC-4626，NAV 不能从合约内部取**
我原先在 `Re.md` 里写「NAV 从 `convertToAssets` 取」，**这是错的**（当时按 A 类通用模式推断的）。实测四个 4626 函数全部 revert。
→ 产品页上 PRICE 那一栏明确标注 **"NAV Oracle"**，说明 **NAV 是外部预言机喂进来的**（与官方文档"Fireblocks 金库余额每日推送 Chainlink"一致）。
→ **必须向项目方要 NAV oracle 的合约地址 + 读取方法**，这是 Re 接入的第一个前置条件。

**2. reUSD 和 reUSDe 共用同一个实现合约**
两个代理都指向 `0xb5276c…21d4`。
→ 好消息：**一套解析适配器能同时覆盖两个代币**，边际成本很低。

**3. 可升级代理 = 新增一条风险**
项目方可以随时替换实现合约逻辑。
→ 要写进 Risk Tab；也建议中台**监控实现合约地址变更**（proxy slot `0x360894a1…82bbc`），变了要告警。

#### 🔴 Ember 的「每日批处理」会打破 PRD 的申购流程


**这段真空期里会发生什么**：
- 用户的 USDC 已经没了

## 六、Re 深度实测：完整解析链路已跑通（2026-08-03）

> 方法：自实现 keccak256 → 从合约 bytecode 反解函数选择器 → `eth_getLogs` 捞真实交易 → 逐笔剖析 receipt。
> **结论：Re 的申购/赎回识别方式已完全确定，且已取得真实交易 hash，无需人工下单。**

### 6.1 完整合约地图

| 角色 | 地址 | 说明 |
|------|------|------|
| **reUSD 代币** | `0x5086bf358635B81D8C47C66d1C8b9E567Db70c72` | 代理 → 实现 `0xb5276c436f65913cd5332de745d04fedeb4a21d4` |
| **reUSDe 代币** | `0xdDC0f880ff6e4e22E4B74632fBb43Ce4DF6cCC5a` | 代理 → **同一个**实现 `0xb5276c…21d4` |
| 🔴 **reUSD 申购入口** | `0x4691c475be804fa85f91c2d6d0adf03114de3093` | 代理 → 实现 `0x06d4acc104b974cd99bf22e4572f48a051e59670`（18,783 bytes） |
| 🔴 **reUSDe 申购入口** | `0xe1886be2ba8b2496c2044a77516f63a734193082` | 两个代币**各有独立入口合约** |
| 申购方法（两个入口通用） | `deposit(address,uint256,uint256)` = **`0x0efe6a8b`** | 自 keccak 反解确认 |
| 申购事件（两个入口通用） | topic0 = `0x8752a472e5…` | ⚠️ 签名未反解出，需 Etherscan ABI |

### 6.2 🔴 代币合约的真实接口 —— 它只是个「可铸造 ERC-20」

从实现合约 bytecode 反解出的函数（已确认 30 个）：

```
ERC-20 标准 : name symbol decimals totalSupply balanceOf transfer transferFrom approve allowance
权限控制    : DEFAULT_ADMIN_ROLE MINTER_ROLE hasRole grantRole revokeRole renounceRole getRoleAdmin
铸造销毁    : mint(address,uint256)  burn(address,uint256)
可升级      : proxiableUUID upgradeToAndCall UPGRADE_INTERFACE_VERSION
其他        : supportsInterface + 一批 OZ v5 自定义错误
```

**没有的东西（重点）**：
- ❌ 没有任何 ERC-4626 函数
- ❌ **没有 `nav()` / `price()` / `exchangeRate()` / `oracle()` 等任何取价函数**
- ❌ **没有 `deposit()` / `redeem()` / `withdraw()`** —— 用户不是直接和代币合约交互的

→ **这解释了为什么 4626 探测全 revert**：reUSD/reUSDe 就是**纯粹的凭证代币**，业务逻辑全在入口合约和链下。
→ 铸造由持有 `MINTER_ROLE` 的运营方执行，NAV 在**入口合约或独立预言机**里。

### 6.4 申购交易的事件结构（解析规格）

以 reUSD 申购为例，一笔交易固定抛 **3 条日志**：

```
tx → to = 0x4691c475…（reUSD 申购入口）｜method = 0x0efe6a8b deposit(address,uint256,uint256)

[0] USDC 合约   Transfer: 用户 → 申购入口        35,000.000000  ← 用户付出的钱
[1] reUSD 合约  Transfer: 0x0 → 用户             32,032.116942  ← 铸出的份额（mint）
[2] 申购入口     自定义事件 0x8752a472e5…                        ← 业务事件（含 NAV？待查 ABI）
```

reUSDe 申购结构完全相同，只是币种换成 **USDe**、入口换成 `0xe1886be2…`。

**→ 给中台的解析规格**：

| 要识别的动作 | 推荐识别方式 | 理由 |
|------------|------------|------|
| **申购** | 监听凭证代币的 `Transfer(from=0x0)` | 最稳。不依赖入口合约地址（项目方可能加新入口） |
| **赎回** | 监听凭证代币的 `Transfer(to=0x0)` | 同上 |
| **用户付出的本金** | 同一笔 tx 里 log[0] 的 Transfer 金额 | 用于算成本基准 |
| **入场 NAV** | `log[0] 金额 ÷ log[1] 金额`（注意 decimals 不同） | 见下方交叉验证 |

⚠️ **decimals 陷阱**：USDC 是 **6 位**，USDe / reUSD / reUSDe 都是 **18 位**。换算时必须分别处理，否则差 10¹² 倍。

### 6.6 ✅ 顺带解决：申购币种的"USDC vs USDe"疑点

我之前发现 CSV 写 USDC、产品页却显示 USDe，列为待确认。**现在答案是：两个都对，各指不同代币。**

| 代币 | 申购币种 | 入口合约 |
|------|---------|---------|
| **reUSD** | **USDC**（`0xa0b86991…eb48`） | `0x4691c475…` |
| **reUSDe** | **USDe**（Ethena 的合成美元） | `0xe1886be2…` |

→ 后台配置时，两个投资品的 From Token **不同**，不能共用配置。

### 6.7 还差的最后一块：NAV Oracle

入口合约实现有 18,783 bytes、159 个 PUSH4 常量，但我的字典（160 个候选签名）**没有命中任何取价函数**。

⚠️ **方法论说明**：从 bytecode 提取 PUSH4 常量会有**假阳性**（任意 4 字节常量都会被当成 selector，比如上面那串 `0x303610xx` 明显是连号的假阳性）。所以"没命中"不代表"不存在"。

```bash
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getStorageAt","params":[
```
