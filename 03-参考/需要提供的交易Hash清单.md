# 需要提供的交易 Hash 清单

> **结论：非常需要。** 目前 7 个协议里，**合约地址基本全缺**，这是所有解析工作的最长前置依赖。
> 一条真实交易 hash 能一次性解决 5 个问题，比问项目方要快得多（不用等回复、不用怕回复的信息过期）。
> 整理时间：2026-07-31

## 一、为什么一条 hash 这么值钱

拿到一条真实的申购交易 hash，我能从区块链浏览器上直接读出：

| 能读出什么 | 解决哪个卡点 |
|-----------|------------|
| **凭证代币合约地址 + vault 合约地址** | 🔴 目前 7 个协议里 6 个缺地址，缺了解析就开不了工 |
| **这笔交易在哪条链上** | 🔴 直接终结「Nest 到底在 BNB 还是 Plume」「Ondo USDY 到底有没有 BNB 部署」这类争论 |
| **调用了哪个方法、抛了哪些事件** | 交易历史解析可以直接照着写，不用猜 |
| **存了多少 / 拿到多少凭证** | 反推入场 NAV，验证我的 NAV 公式对不对 |
| **申购路径是直连还是过 router** | 决定我们能不能把这笔交易正确识别成"申购"（过聚合器的话签名完全不同） |

**你的 hash 相比"我自己在浏览器上随便找一个持有人的交易"的独特价值**：能保证是**我们真正要接的那个池子**。同一个协议往往有好几个 vault（比如 Ember 有 EARN 和 PPLUS 两个，Ondo 有 100+ 个代币），我从外部看不出来该接哪个。

| # | 协议 | 想要什么交易 | 解决什么 |
|---|------|------------|---------|
| **1** | **Ondo USDY** | ① 一笔**申购**（USDT → USDY）<br>② **持有一段时间后的任意一笔转账**，或直接告诉我"你的 USDY 余额有没有自己变多过" | 🔴 **判定它是 A 类还是 B 类**。<br>如果余额自己变多 → rebasing（B 类），**详情页不能配 NAV 曲线**；<br>如果余额不变、只是变值钱 → A 类，NAV 曲线正常做。<br>顺带确认 BNB 链上到底有没有部署 |
| **2** | **Nest nOPAL** | 一笔**申购**（USDT → nOPAL） | 🔴 终结链冲突。表格写 BNB，官方文档只说 Plume / Solana / Ethereum / Avalanche。**链搞错了整套解析全废** |

## 三、比 hash 更方便的两个替代方案

如果你不方便逐条找 hash：

**方案 A：直接给钱包地址（最省事）**
给我一个地址，我能在浏览器上把这个地址的**全部交易历史**拉出来，一次拿到所有协议的信息。

⚠️ **但要注意隐私**：地址是公开的，给出去等于公开这个地址的**全部持仓、全部交易历史、总资产**（包括跟本项目无关的）。
→ **建议**：如果这些申购是用你的主钱包做的，就别给地址，改给单条 hash（单条 hash 只暴露那一笔交易）。如果是测试账号 / 小额专用账号，给地址最方便。

**方案 B：给产品页截图**
很多产品页会直接显示合约地址。你在 App / 网页上打开产品详情，把"合约地址 / Contract"那一栏截图给我也行——尤其是 **ember.so**（我抓不到）和 **reale.finance**（也 403）。

## 四、给了之后我会做什么

1. 逐条在浏览器上解出：链 + vault 地址 + 凭证代币地址 + decimals + 方法签名 + 事件结构
2. 回填到各协议文档的「5. 链上机制与凭证代币」和「6.3 需向项目方索取」（能自己查到的就不用再问项目方了）
3. **实测验证** NAV 取数函数（`convertToAssets` 等）是否真的能调通，而不是只凭文档说"应该是标准 4626"
4. 更新每个协议的**解析类型判定**（A / B / C），特别是 Ondo 和 DMZ 这两个待定的
5. 把确认过的地址整理成一张表，直接可以交给中台解析同学开工

## 五、安全提醒（顺便说一句）

- **交易 hash 和钱包地址都是公开信息**，给出来不会有任何资产风险
- 🔴 **但助记词 / 私钥 / Keystore 文件绝对不要给任何人**（包括我）。任何流程都不需要这些东西
- 我需要的只是"读"链上公开数据，不涉及任何签名或操作
